# The engine's sandbox: what low integrity does not do (finding H2), and the next step

The engine runs with a low-integrity copy of the host's token inside a Job Object. That stops it writing to the host's files, but it does not stop it reading them: a model that gets code execution inside `llama-server` can read anything the user can read, including the agent's state folder and DPAPI blobs, and DPAPI opens them for it because the token is still the user's. The next release should run the engine with less than the user's identity, in an AppContainer or under a restricted token (restricting SIDs with the user's SID deny-only, plus low integrity). Either one needs: read access granted explicitly to the engine folder and the one model file (an ACL entry for the AppContainer SID or restricting SID, set by the agent per load and removed after); a loopback exemption, because an AppContainer cannot be reached on 127.0.0.1 without one (`NetworkIsolationSetAppContainerConfig`, or keep the socket on the agent's side and hand it over); and access to the GPU device, which is the real unknown, since CUDA opens `\\.\NvAdapter`-style devices and registry keys that an AppContainer may be denied. To test it: start `llama-server --list-devices` under the new token through `internal/supervisor`, then a real load with `gpu_layers: "all"`, and require the PID in `nvidia-smi --query-compute-apps` as the agent already does; then run `cmd/lowiltest`-style probes as that token, which must fail to read a file in the user's profile and fail to open a DPAPI blob. If CUDA cannot run under it, the fallback stays low integrity, and the host's explicit opt-in remains the only way to anything weaker. This can ship later because the daily check of the signed latest release lets a hacked hub no longer hide the update that brings it.
